# 05 — Asset Pipeline (AI-Generated 3D Assets)

The end state per the design brief: game assets generated by AI (text → 3D),
validated automatically, optimized, and imported into the build — all triggered
from a phone, all executed in the cloud. The vertical slice ships **procedural**
geometry; this document defines the pipeline that progressively replaces it.

## Design principles

1. **Assets are addressed by stable ids** (`tree_pine`, `rock_large`,
   `extractor_machine`). Content JSON never names a file — it names a *thing*.
   Geometry source can therefore swap (procedural → GLB → better GLB) without
   touching game data.
2. **Nothing generated enters the build unvalidated.** The gate is the pipeline,
   not a human eyeball.
3. **Dev-time only.** Generation runs in CI / from the developer's phone via
   workflow dispatch. The shipped APK contains only processed assets — no API
   keys, no prompts, no provider SDKs.
4. **Fail-open at runtime.** If a GLB is missing or fails to load at runtime the
   world falls back to the procedural kit piece (the `WorldKitProvider` chain).

## Provider seams (implemented today)

`core/providers/AssetProviders.kt`:

| Interface | Purpose | Status |
|-----------|---------|--------|
| `WorldKitProvider` | Resolve kit piece id → geometry | `ProceduralKitProvider` (live); `GlbKitProvider` (future) |
| `TextModelProvider` | Prompt → structured text (prompts, names, lore) | placeholder |
| `ImageProvider` | Prompt → image bytes (icons, textures) | placeholder |
| `ThreeDModelProvider` | Prompt → GLB bytes | placeholder |
| `AssetProcessingProvider` | Validate + optimize + LOD a GLB | placeholder |
| `AnimationProvider` | Clip for a model id | placeholder |

Each becomes a concrete implementation backed by a cloud API (selection is a
Phase 6+ decision — the abstraction exists precisely so providers are
swappable).

## The pipeline (target flow)

```
PROMPT (asset brief, JSON in repo: tools/asset-briefs/<id>.json)
  │
  ▼ generate (ThreeDModelProvider, CI job, workflow_dispatch from phone)
GLB (raw)
  │
  ▼ validate  ── mesh sanity: watertight-ish, size bounds, axis orientation,
  │              material count, vertex budget by importance class
  │              (hero machine ≤ 12k tris, prop ≤ 800, scatter ≤ 300)
  ▼ optimize  ── (AssetProcessingProvider) meshopt/draco, texture atlas +
  │              ETC1S/ASTC, pivot normalization, scale normalization
  ▼ LODs      ── decimate: LOD0/LOD1/LOD2 (~100%/50%/25%)
  ▼ import    ── app/src/main/assets/models/<id>.glb
  ▼ manifest  ── assets/models/manifest.json entry { id, file, lods, budget,
  │              validated: true, source: "prompt-hash" }
  ▼ game      ── GlbKitProvider resolves the id from the manifest; fallback =
                 procedural kit piece
```

## The manifest (schema shipped today)

```json
{
  "version": 1,
  "assets": [
    {
      "id": "rock_large",
      "file": "models/rock_large.glb",
      "source": "3dgen#b7f2…",
      "lodCount": 3,
      "vertexBudget": 800,
      "validated": true
    }
  ]
}
```

The manifest is the **only** import surface — the game never scans a directory,
so partial or in-flight generations cannot leak into a build.

## Collision + modularity data (per asset, phase 6+)

Generated assets ship a sidecar `<id>.meta.json` (validated with the mesh):

- bounding box + origin (feet pivot)
- collision primitives (box/capsule per part, not per triangle)
- connection points (for belt/pipe/track snapping)
- placement constraints (max slope, snapping grid, biome)
- LOD distances + scale range

World assembly then composes modular pieces from `world.json` exactly as it
does with procedural pieces today — placement data outlives geometry.

## CI workflows (planned)

| Workflow | Trigger | Job |
|----------|---------|-----|
| `asset-generate` | `workflow_dispatch` with asset id | provider call → raw GLB artifact |
| `asset-process` | raw GLB artifact | validate → optimize → LOD → manifest PR |
| `asset-verify` | manifest PR | renders turnaround screenshots (headless GPU runner) for human review from the phone |

The merge of a manifest PR is the "accept" action — done from the GitHub mobile
app.

## Why procedural-first was right for the slice

- Zero build-time dependencies on external services; the slice is fully
  reproducible from source.
- The kit ids, palette resolution, world placement format and provider seams are
  identical for GLB assets, so nothing built today is thrown away.
- The visual baseline (stylized low-poly, flat colors, one material per color)
  is a coherent look, not a placeholder look.
